# Interleaving phase-one gradient consumption with AOTAutograd backward: findings

## 1. Causal explanation of your trace

Your hypothesis is correct and it's not a quirk — it's the documented contract of AOTAutograd.

When `torch.compile` traces a model, AOTDispatcher (AOTAutograd) captures forward and backward as a **joint graph**, then a **partitioner** splits it into a `CompiledFunction.forward` and a `CompiledFunction.backward`, wrapped in a single `torch.autograd.Function`. The backward's signature is fixed at trace time: PyTorch's own docs describe the mechanism as AOTDispatcher rewriting `train`'s forward/backward "[using] torch.autograd.Function" and Inductor compiling that pair as one optimized unit ([Compiled Autograd tutorial](https://docs.pytorch.org/tutorials/intermediate/compiled_autograd_tutorial.html)). Every parameter that requires grad is a **primal** to that joint graph, and the AOTAutograd contract is that `CompiledFunction.backward` returns exactly one gradient tensor per primal, in a fixed output order — this is confirmed directly in a currently-open partitioner-ordering bug: *"CompiledFunction.backward gradient return order must match the input order to CompiledFunction.forward"* ([pytorch#144376](https://github.com/pytorch/pytorch/issues/144376)).

This is the mechanism, not an accident of scheduling: the `min_cut_rematerialization_partition` — the thing that decides what gets recomputed vs. saved — operates on **intermediate activations**, trading recompute for memory ("[the partitioner] performs smarter fusion-aware recomputation... fewer outputs in the forward pass") ([functorch AOT Autograd docs](https://docs.pytorch.org/functorch/stable/notebooks/aot_autograd_optimizations.html)). It has no lever over primal gradients, because those aren't optional intermediates the partitioner is free to discard — they're the *definition* of what the backward graph must produce. So your 92 gradients aren't "scheduled late" by some suboptimal heuristic; they're required outputs of one atomic compiled function, and Inductor's codegen doesn't hand you a callback per-output as it fills the return tuple — the whole backward executes as one scheduled kernel sequence, and nothing is visible to Python (hence to your hook) until that sequence returns. That's why your probe saw cumulative peak already at 7.02 GB at the *first* callback: the backward had already run to completion by the time eager `AccumulateGrad` nodes started firing.

The post-backward numbers you see (current allocation flat at ~4.75 GB through all 92 callbacks, draining monotonically in release mode) are consistent with this: your hook frees `.grad`, but the pile was already fully materialized before any hook could run, so freeing after the fact changes *post-backward* residency, not *peak*. This matches the distinction PyTorch's own optimizer-in-backward tutorial makes about eager mode — freeing gradients as they're produced moves the peak earlier, into backward, because that's the only way the trick works: *"the peak has moved... near the start of the backward step, when we still have activations in memory"* ([optimizer-in-backward tutorial](https://docs.pytorch.org/tutorials/intermediate/optimizer_step_in_backward_tutorial.html)). Under compile, there is no "during backward" checkpoint for you to hook — backward is one opaque scheduled unit.

## 2. Answers to the specific sub-questions

**(1) torch.compile optimizer-in-backward support.** None exists as a compile-aware primitive. `apply_optimizer_in_backward` and `register_post_accumulate_grad_hook` are eager mechanisms — they install a hook on the `AccumulateGrad` node via `param.view_as(param).grad_fn.next_functions[0][0].register_hook(...)` ([pytorch#76464](https://github.com/pytorch/pytorch/issues/76464); [apply_optimizer_in_backward.py source](https://github.com/pytorch/pytorch/blob/main/torch/distributed/optim/apply_optimizer_in_backward.py)). Under plain `torch.compile`, that hook still fires only after the compiled backward returns — it does not get pulled into the compiled graph.

**(2)+(3) `register_post_accumulate_grad_hook` under AOTAutograd, and whether hooks get captured into the compiled backward.** Under plain `torch.compile` (no Compiled Autograd): not captured — this is exactly your observed structural gap. Under **Compiled Autograd** specifically: yes, captured — a 2024 issue shows the traced FX graph containing an `accumulate_grad_` node fused with the hook's own ops in the same graph (`all_reduce_result = l_inputs_2_grad / 2; copy_ = ...`) ([pytorch#119906](https://github.com/pytorch/pytorch/issues/119906)). This is real and important, but two caveats: (a) the same issue reports the dependency edges between `accumulate_grad_` and the hook ops are *not* correctly modeled, so the compiler can legally reorder the hook before the accumulation completes — a live correctness bug, not a hardened primitive; (b) nothing in the public record demonstrates this capture actually lowers *peak* memory rather than just fusing kernel launches. I could not find a benchmark measuring `max_memory_allocated` for compiled-autograd-captured hooks against the eager baseline. Treat "Compiled Autograd interleaves the hook into the schedule" as structurally plausible but empirically unverified for your peak-memory claim.

**(4) PyTorch "optimizer in backward" APIs and compile compatibility.** `torch.distributed.optim.apply_optimizer_in_backward` and torchtune's `OptimizerInBackwardWrapper` ([torchtune memory.py](https://pytorch.org/torchtune/0.1/_modules/torchtune/utils/memory.html)) are both the same `register_post_accumulate_grad_hook` pattern underneath, both eager-hook-based, neither documented as compile-integrated. `apply_optimizer_in_backward` also has an open, acknowledged limitation with gradient accumulation ([pytorch#124523](https://github.com/pytorch/pytorch/issues/124523)) — a different problem than yours, but it signals this whole API family is still first-class-eager, not first-class-compiled.

**(5) Compiled Autograd — does it change the boundary?** Partially, and it's the most promising lever in released PyTorch, with real caveats. Compiled Autograd works by tracing the *entire* C++ autograd execution — including hooks — into one larger graph at runtime, rather than relying on AOTAutograd's ahead-of-time capture: *"Compiled Autograd addresses these limitations by directly integrating with the autograd engine, allowing it to capture the full backward graph at runtime"* ([Compiled Autograd tutorial](https://docs.pytorch.org/tutorials/intermediate/compiled_autograd_tutorial.html)). Nodes from the original AOTAutograd-compiled backward appear as `aot0_`-prefixed subgraph nodes inside the larger Compiled Autograd graph — meaning your per-parameter hook, if it appears as a traced op adjacent to that parameter's `accumulate_grad_` node, is a graph-local operation subject to Inductor's ordinary buffer-liveness scheduling, not something that has to wait for a separate Python callback after a fixed-shape tuple return. That's the theoretical case for it solving your problem. Against it: (a) the ordering-safety bug above; (b) Compiled Autograd explicitly documents added cache-lookup overhead and higher recompile sensitivity; (c) it currently recompiles once per `zero_grad()` call in some hook configurations, an open bug ([pytorch#118435](https://github.com/pytorch/pytorch/issues/118435)); (d) it is explicitly still "under active development and not yet compatible with all existing PyTorch features," with feature support tracked on its own landing page rather than guaranteed stable. There is no published peak-memory number for this configuration anywhere I found.

**(6) AOTAutograd partitioning / options to avoid returning all parameter gradients as outputs.** No such option exists, for the structural reason in §1 — parameter gradients are primal outputs, not partitioner-discretionary intermediates. `min_cut_rematerialization_partition` and its cousins only touch the activation/intermediate side of the joint graph.

**(7)+(14) Custom autograd Functions / custom ops that consume a gradient before it becomes a persistent leaf output — the actual lever.** This is real, current, and where the answer lives. `torch.library.custom_op` + `register_autograd` lets you define an op whose `backward` is arbitrary PyTorch-op composition, traced into the graph like any other node ([Custom Python Operators tutorial](https://docs.pytorch.org/tutorials/advanced/python_custom_ops.html)). The mechanism that solves your problem: insert the custom op as the node that receives the *full* weight-shaped gradient, do your projection/Adafactor-conditioning/Oja-tracking arithmetic on it there, and return something rank-sized (or a zero/`None`) as the op's own backward output. Because the full gradient never becomes one of `CompiledFunction.backward`'s *returned* primal gradients — it's consumed and discarded as a dead intermediate inside a graph node — it becomes subject to Inductor's ordinary liveness-based buffer scheduling instead of being pinned alive until the whole backward returns. This is the precise distinction your research question is chasing: "consumed inside the graph" vs. "returned then consumed."

Two hard constraints surfaced by direct evidence, not speculation:
- The custom op's backward "must be a composition of PyTorch-understood operations" ([Custom Python Operators tutorial](https://docs.pytorch.org/tutorials/advanced/python_custom_ops.html)) — arbitrary in-place mutation of long-lived optimizer-state tensors from inside a traced backward is exactly the kind of thing that currently breaks: there's an open, explicitly-scoped bug for "mutating backward input of autograd function is not supported by torch.compile" ([pytorch#141111](https://github.com/pytorch/pytorch/issues/141111)), and a related SAC (selective activation checkpointing) issue about in-place mutation not being preserved correctly under the joint-graph/partitioner model ([pytorch#113737](https://github.com/pytorch/pytorch/issues/113737)). Your projected-momentum and Oja-state updates are exactly this kind of mutation.
- Plain `torch.autograd.Function` subclasses (as opposed to `torch.library.custom_op`) have a documented, distinct failure mode: `torch.compile` does not fuse across their boundary in backward — confirmed with a minimal reproducer showing no backward speedup despite forward speeding up normally ([pytorch#101937](https://github.com/pytorch/pytorch/issues/101937)), and AMP-wrapped custom forward/backward (`custom_fwd`/`custom_bwd`) fails to trace into a single graph at all ([pytorch#114693](https://github.com/pytorch/pytorch/issues/114693)). If you go this route, use `torch.library.custom_op`, not a raw `Function` subclass, and expect a graph break at that boundary rather than true fusion — which is fine for your purposes (see §9) but means you're not getting Inductor fusion gains on the gradient-conditioning arithmetic itself.

**(8) `saved_tensors_hooks`, AC variants, DDP/FSDP hooks, autograd engine callbacks.** These affect *activation* materialization timing, not the parameter-gradient-output problem — orthogonal to your issue, confirmed by nothing in the primary sources suggesting otherwise. Worth knowing for composability once phase-one is solved: activation checkpointing composes cleanly with gradient-floor elimination in the one paper that measures both together (see §11) — the two costs are additive and independently addressable.

**(9)+(12) Selective compilation / graph breaks / regional compilation / different checkpoint implementations — does eager interleaving become possible?** Yes, and this is your lowest-risk released-PyTorch path if the custom-op route above proves too fragile. TorchTitan's documented practice is "regional compilation... applies `torch.compile` to each individual TransformerBlock," explicitly chosen because it gets "a full graph (without graph breaks) for each region" while stacking compiled regions ([TorchTitan paper](https://arxiv.org/pdf/2410.06511)). If you compile per-block rather than end-to-end, each block's `CompiledFunction.backward` returns only that block's parameter gradients, not all 92 at once — the AOTAutograd primal-output pile shrinks to per-block scope, and between blocks you're back in eager territory where your existing `register_post_accumulate_grad_hook` mechanism already works (you proved this yourself: 13.3% peak reduction, peak moved from layer 0 to layer 15). This doesn't eliminate the pile, but it bounds it to one block's worth of gradients instead of the whole model's, and it's the same tactic `fullgraph=False` + strategic `torch._dynamo.graph_break()` calls give you at finer granularity if per-block is still too coarse. This costs you cross-block fusion opportunities in exchange.

**(10) Frameworks/optimizers demonstrating optimizer-in-backward + compile with real peak-memory wins.** This is the center of gravity of what I found, and it reframes the question. Nobody demonstrates optimizer-in-backward *cooperating with* AOTAutograd's compiled boundary to reduce peak memory — the two credible groups that actually solve your underlying problem (FlashOptim, FORGE — see §11) both **bypass AOTAutograd's parameter-gradient materialization entirely** rather than negotiating with it. GaLore's low-rank projection happens in `optimizer.step()`, after full materialization — no help. `optimi`'s gradient-release library and torchtune's wrapper are both the same eager hook pattern you're already using, with no compile story. DeepSpeed and Composer's memory techniques (ZeRO stages, activation offload) target optimizer-state and activation pools, not the gradient-materialization-under-compile boundary specifically.

**(11) Recent issues/patches on "AOTAutograd returns all parameter gradients before AccumulateGrad."** No issue titled or scoped exactly that way exists as a tracked bug — because it isn't a bug, it's documented behavior (§1, §6). The closest related open work is the hook-ordering and hook-capture-correctness issues cited above (#144376, #119906, #118435), which are about *Compiled Autograd's* handling of hooks, not about AOTAutograd's fundamental contract.

**(13) Is there a sanctioned way to compile only forward and leave backward eager?** Not directly as a flag. The closest sanctioned mechanisms are (a) regional/selective compilation (§9) — compile forward-heavy subregions and let the rest of the graph, including its backward, stay eager at the seams; (b) the documented `torch.compile` + `Compiled Autograd` split where you can compile forward and backward with *different* compiler configs — *"you can use different compiler configs for the two compilations, for example, the backward may be a fullgraph even if there are graph breaks in the forward"* ([Compiled Autograd tutorial](https://docs.pytorch.org/tutorials/intermediate/compiled_autograd_tutorial.html)) — but that's configuring two separate compilations, not "compiled forward, eager backward." There is no supported `torch.compile(model, compile_backward=False)`-style toggle.

## 3. The actual state of the art: bypass, don't negotiate

The most load-bearing finding in this research isn't a PyTorch internals answer — it's that the two most credible pieces of prior work on exactly your problem (Databricks' **FlashOptim**, arXiv:2602.23349, Feb 2026, and the newer **FORGE**, arXiv:2606.22932, Jun 2026) both concluded the AOTAutograd boundary isn't worth fighting and routed around it entirely.

**FlashOptim** ([paper](https://arxiv.org/abs/2602.23349), [code](https://github.com/databricks/flashoptim)) is close kin to what you're already doing — bf16 weight storage with tight error-correction bounds plus 8-bit state quantization, "reduces AdamW memory from 16 bytes to 7 bytes per parameter, or 5 bytes with gradient release." Per FORGE's characterization of it as a baseline, FlashOptim's gradient-release path "fire[s] only once a whole parameter's gradient has materialized... and pay[s] one optimizer launch per parameter" — i.e., it is the same `register_post_accumulate_grad_hook` per-parameter pattern you're using, with the same structural ceiling under compile that you've found. It is not compile-integrated in a way that changes the AOTAutograd boundary.

**FORGE** ([arXiv:2606.22932](https://arxiv.org/pdf/2606.22932)) is the one paper I found that actually eliminates the gradient-materialization floor under compile-adjacent conditions, and it does it by **never entering PyTorch's autograd graph for the weight gradient at all**. It replaces the linear layer's backward with a single hand-written Triton kernel that forms the weight gradient one `128×128` tile at a time in GPU registers, applies the (element-wise-separable) optimizer update to that tile in-register, and writes back only the updated weight/moment tiles — "the gradient tile is consumed the instant it is produced and never becomes a tensor." It is not a `torch.compile`/AOTAutograd trick; it's a custom kernel that subsumes both the wgrad GEMM and the optimizer step, invoked in place of the standard linear-layer backward. Their own framing states this directly: standard training "separates gradient computation from the optimizer step into two sequential phases, so all layers' gradients must coexist in memory at the forward-backward-step boundary... the gradient floor is not an oversight; it is structural." Their measured result on Llama-3.1-8B (H200, BS=1, SEQ=512): fused AdamW peaks at 75.0 GiB, FlashOptim's per-parameter gradient-release peaks at 42.3 GiB (closest baseline on memory but "still 7 GiB above FORGE... because its fusion happens at per-parameter granularity, after the gradient has materialized" — this is your exact finding, independently confirmed), and FORGE reaches 35.4 GiB while being *faster*, not slower, than fused AdamW (99.1ms vs. 150.9ms/step) because it also eliminates the separate optimizer kernel launch.

Two structural constraints on FORGE's technique that matter for whether it maps onto UsuiTrack: (a) it requires the optimizer update to be **element-wise-separable** — coordinate `(p,q)`'s new value depends only on that coordinate's `(W,G,S)`. AdamW, SGD, Lion, RMSprop qualify; Adafactor, LAMB, SM3, and anything that mixes coordinates through a row/column/block/global statistic do not, and are explicitly excluded from full fusion in their own taxonomy. Your Oja/Aurora tracking and Grassmannian projection are **not** element-wise — they're explicitly cross-coordinate (rank-space projection is a matrix operation over the whole tile). This means FORGE's specific tile-fusion trick doesn't transfer wholesale to UsuiTrack's phase one; what transfers is the *architectural move* — write a custom fused kernel that owns the gradient-formation-to-consumption path end-to-end, rather than trying to get a generic hook to run inside someone else's compiled graph. (b) it requires the weight to have exactly one gradient consumer per step, which rules out tied embeddings/MoE — worth flagging since you're doing continued pretraining on LFM-1.2B and should check whether any 2D matrices are weight-tied.

## 5. Where each candidate stands

- **Released PyTorch:** #3 (regional compilation) and #5 (targeted graph breaks) are fully available today, low-risk, and directly supported by TorchTitan's documented practice. #2 (`custom_op` in-graph) is available as an API but the specific pattern you need — mutating persistent state from inside a traced backward — runs into open, acknowledged compiler bugs, not settled behavior.
- **Experimental/nightly:** Compiled Autograd (#4) is the only mechanism that structurally *could* interleave a hook into the compiled schedule, and it does capture hooks into the graph as of the 2024 issue — but it ships with its own stated caveats ("under active development, not yet compatible with all existing PyTorch features") and no memory benchmark exists for your use case.
- **Private/internal APIs:** none surfaced. Nothing found suggests Meta or any lab has an unreleased AOTAutograd flag for this.
- **Requires compiler changes:** none of the released mechanisms solve this at the granularity you want (per-parameter, inside one whole-model compiled backward) without either (a) bypassing autograd for the tracked tensors (#1), or (b) shrinking the compiled unit so the "whole model" pile never forms (#3/#5).

## 6. Smallest credible experiment to run next

Don't build the FORGE-style kernel first — validate the *architectural* hypothesis cheaply first, since it's the one with the least existing evidence:

1. Take your current LFM-1.2B setup and wrap the model in **per-transformer-block `torch.compile`** (TorchTitan's pattern: `for block in model.blocks: block = torch.compile(block)`, leave everything else eager), keeping your existing `register_post_accumulate_grad_hook` phase-one exactly as-is.
2. Rerun your identical probe (before/after allocator snapshots at each hook callback) and check two things: (a) does the cumulative-peak-at-first-callback number drop from 7.02 GB toward something closer to your eager 7.2 GB baseline's *shape* (peak late in backward, not immediately at trace start)? (b) does current-allocation stop being flat across all 92 callbacks — i.e., does it start draining incrementally as blocks complete, the way it does post-backward today?

If (a)/(b) both hold, you've confirmed the pile shrinks to per-block scope under compile without touching autograd internals at all, and you can decide whether per-block granularity is good enough or whether you need finer graph breaks inside a block (candidate #5) or the full bypass (candidate #1). If the pile *doesn't* shrink — e.g., if Dynamo silently fuses adjacent compiled blocks back into one backward region, which is a known possible failure mode of naive regional compilation — that's a fast, cheap negative result before you invest in a custom kernel.

## 7. Recommended implementation path

Two tracks, not mutually exclusive:

- **Near-term (this sprint):** candidate #3, per-block regional compilation. It costs you nothing you don't already have — your hook mechanism is proven, you're just changing where `torch.compile` draws its boundary. Expected outcome, based on the TorchTitan precedent and your own eager numbers: a partial recovery of your 13.3%/960 MB eager saving, bounded by block granularity rather than full-model granularity. This is the low-risk move that gets you *something* under compile without new failure modes.
- **Medium-term, if #3's saving isn't enough:** candidate #1, a custom fused kernel modeled on FORGE's architecture but adapted for UsuiTrack's non-element-wise phase one. The adaptation: FORGE fuses gradient-formation + optimizer-update because AdamW is element-wise; you can't fuse the Grassmannian projection into a GEMM epilogue the same way, but you *can* fuse gradient-formation + Adafactor-conditioning + the *linear* parts of the projection (which are matmuls against a low-rank basis, themselves GEMM-shaped) into one kernel that never writes the full gradient to HBM, then hand off only the rank-sized result to your existing eager Oja/Aurora batching. This is real kernel-engineering work, not a config change, and worth scoping only after #3's experiment tells you how much headroom is actually still on the table.

## 8. Blunt conclusion

Current public PyTorch cannot interleave phase-one computation with AOTAutograd's compiled backward at per-parameter granularity without either shrinking the compiled unit (regional compilation / graph breaks) or bypassing standard autograd differentiation for the tracked tensors (a custom fused kernel). There is no flag, partitioner option, or documented compiler internal that will let a `register_post_accumulate_grad_hook`-style callback run *inside* a whole-model compiled backward and change peak memory — the primal-gradient-output contract is fundamental to how AOTAutograd is specified, not a scheduling accident. Compiled Autograd is the one mechanism that structurally gestures at solving this, and it's real enough that the hook-fusion-into-graph behavior is already observable in the tracer output — but it's unproven for your metric, sits on top of at least one open correctness bug in exactly the code path you'd need, and nobody has published a `max_memory_allocated` number for it doing what you want. The people who've actually solved your class of problem under real memory pressure (FlashOptim, FORGE) didn't negotiate with AOTAutograd at all — they either accepted the per-parameter-after-materialization ceiling you've already found, or wrote a kernel that never lets PyTorch's autograd own the weight gradient in the first place. That's the real fork in the road: stay eager and accept the ceiling, shrink the compiled unit for partial relief, or go around autograd entirely for the tensors that matter.
